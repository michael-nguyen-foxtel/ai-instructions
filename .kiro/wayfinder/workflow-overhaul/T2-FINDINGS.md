## Why skill-leaning practitioners prefer skills

- **Skills package procedural knowledge, not a whole new agent.** Anthropic frames a skill as "an onboarding guide for a new hire" and explicitly positions it as the alternative to "building fragmented, custom-designed agents for each use case" — you specialise one general-purpose agent with composable capabilities instead of standing up a bespoke agent per task ([Anthropic, Equipping agents](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).
- **Progressive disclosure keeps context cheap.** Only the `name` + `description` of every skill is preloaded into the system prompt; the `SKILL.md` body loads only when the skill is judged relevant, and bundled files (scripts, references) load only as needed. Anthropic calls progressive disclosure "the core design principle that makes Agent Skills flexible and scalable" and notes the bundled context is "effectively unbounded" because it isn't all resident ([Anthropic, Equipping agents](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).
- **Composability and portability.** Skills are "composable, scalable, and portable" folders; a single agent can compose several. Anthropic later published the format as an open cross-platform standard (agentskills.io, Dec 2025), so the same skill runs across Claude.ai, Claude Code, the Agent SDK, and third-party clients ([Anthropic, Equipping agents](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).
- **They run in the current agent's context — human stays in the loop.** Claude Code's own guidance says to "consider Skills when you want reusable prompts or workflows that run in the main conversation context rather than isolated subagent context" ([Anthropic, Create custom subagents — "Choose between subagents and main conversation"](https://docs.anthropic.com/en/docs/claude-code/subagents)). Because the work happens inline, the human sees every step rather than only a returned summary.
- **Small, inspectable, low-overhead (Pocock's stated reason).** Matt Pocock's whole thesis is that skills are "intentionally small… You can read them, edit them, and understand what they are asking the agent to do… The workflow stays observable." He argues "large frameworks can hide too much. They burn context, obscure the instructions, and make it harder to understand why the agent did what it did" ([Pocock, AI Skills for Real Engineers](https://www.aihero.dev/skills-post)).
- **Value is in composition, not any single skill.** Pocock: the skills' "real value is in how they compose" into "a software practice, not a pile of prompts" (`domain-model → to-prd → to-issues → tdd`) ([Pocock, AI Skills for Real Engineers](https://www.aihero.dev/skills-post)).
- **A skill changes *how* the agent works each run, not *what* it outputs.** Pocock's `writing-for-agents` reference states the point of a skill is that "the agent takes the same *process* every run rather than producing the same output," and its default authoring move is deletion of "no-ops" that pay context load without changing behaviour ([Pocock, /writing-for-agents](https://www.aihero.dev/skills-writing-for-agents)).

## The case for agent-first / sub-agents

- **Context protection / isolation is the headline reason.** Anthropic's docs say to use a subagent "when a side task would flood your main conversation with search results, logs, or file contents you won't reference again: the subagent does that work in its own context and returns only the summary." Each runs in "its own context window with a custom system prompt, specific tool access, and independent permissions" ([Anthropic, Create custom subagents](https://docs.anthropic.com/en/docs/claude-code/subagents)).
- **Parallelism for thoroughness.** Anthropic's Research feature spawns parallel subagents, each with its own context window chasing one thread, and beat single-agent Opus 4 by **90.2%** on their internal research eval — the primary benefit stated is "thoroughness, not speed" (covering a larger search space than one context can hold) ([Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/built-multi-agent-research-system); [Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- **Three named situations where multi-agent consistently wins.** Anthropic's decision framework: (1) **context pollution** degrades performance, (2) tasks **run in parallel**, (3) **specialization** improves tool selection or task focus. "Outside these situations, the coordination costs typically exceed the benefits" ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- **Tool/permission scoping is a first-class benefit.** Subagents let you "enforce constraints by limiting which tools a subagent can use" and scope MCP servers/permissions per agent — Anthropic notes an agent with 20+ tools "struggles to select the appropriate one," which specialised toolsets fix ([Anthropic, Create custom subagents](https://docs.anthropic.com/en/docs/claude-code/subagents); [Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- **Conflicting personas/instructions.** "A customer support agent needs to be empathetic… a code review agent needs to be precise and critical." When one agent must switch between conflicting behavioural modes, separate system prompts produce more consistent results ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- **The verification-subagent pattern.** A blackbox verifier "does not need to understand why the artifact was built" — it needs minimal context transfer, which is exactly why it works well as a separate agent ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- **What sub-agents solve that a skill cannot:** a skill runs in the *shared* main context, so it cannot (a) keep verbose intermediate work out of the main window, (b) run truly in parallel with independent context windows, or (c) enforce a hard toolset/permission boundary. Those three are precisely the sub-agent value props above.

### The cost (stated by the same sources — this is not free)

- Multi-agent uses **3–10× more tokens** than single-agent for equivalent tasks (duplicated context, coordination messages, summarising for handoffs), and often takes **longer overall** despite parallelism ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- Handoffs lose context — the "telephone game." Anthropic saw teams whose role-split agents "spent more tokens on coordination than on actual work" ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- General principle: "find the simplest solution possible, and only increas[e] complexity when needed. This might mean not building agentic systems at all" ([Anthropic, Building Effective AI Agents](https://www.anthropic.com/research/building-effective-agents)).

## The core mechanism (context ownership)

The hypothesis is **substantially correct per Anthropic's own docs**, with two refinements:

- **SKILL side — confirmed.** A skill is loaded *into the current agent's context window* via progressive disclosure and runs inline with the existing conversation, tools, and history. Claude Code's own guidance recommends skills "when you want reusable prompts or workflows that run in the main conversation context rather than isolated subagent context" ([Anthropic, Create custom subagents](https://docs.anthropic.com/en/docs/claude-code/subagents); [Anthropic, Equipping agents](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). "Zero handoff cost, human stays in the loop" is a fair characterisation because there is no separate context to hand off to.
- **SUB-AGENT side — confirmed.** "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read… only its final message returns to the parent." It has a curated system prompt, a `tools`/`disallowedTools` allowlist, independent `permissionMode`, and scoped MCP servers ([Anthropic, Create custom subagents — "What loads at startup"](https://docs.anthropic.com/en/docs/claude-code/subagents); [Claude Code SDK, Subagents in the SDK](https://platform.claude.com/docs/en/agent-sdk/subagents)). The handoff/summary cost is real and quantified (3–10× tokens).
- **Refinement 1 — the two are composable, not exclusive.** A subagent can *preload* skills (the `skills:` frontmatter field injects full skill content at startup) or discover and invoke them at runtime via the Skill tool. So "skill vs agent" is not strictly either/or: a defined agent is often *a curated context + toolset that itself runs skills* ([Anthropic, Create custom subagents — "Preload skills into subagents"](https://docs.anthropic.com/en/docs/claude-code/subagents)).
- **Refinement 2 — a "fork" is the exception to fresh context.** Claude Code's fork subagent inherits the *entire* conversation, system prompt, tools, and model, so it is a sub-agent that does **not** pay the re-briefing cost — only its tool calls stay out of the main window. This blurs the clean "sub-agent = fresh context" line: isolation of *output noise* and isolation of *input context* are separable ([Anthropic, Create custom subagents — "Fork the current conversation"](https://docs.anthropic.com/en/docs/claude-code/subagents)).

## Documented dividing line (if any)

There **is** explicit guidance, and it lines up closely with the question's framing. Claude Code's "Choose between subagents and main conversation" section states:

- Use the **main conversation** (i.e. a skill/inline) when: the task needs frequent back-and-forth or iterative refinement; multiple phases share significant context (planning + implementation + testing); it's a quick targeted change; or latency matters (a non-fork subagent starts fresh and must re-gather context).
- Use **subagents** when: the task produces verbose output you don't need in the main context; you want to enforce tool restrictions/permissions; or the work is self-contained and can return a summary.
- And directly: "Consider Skills instead when you want reusable prompts or workflows that run in the main conversation context rather than isolated subagent context."
  ([Anthropic, Create custom subagents](https://docs.anthropic.com/en/docs/claude-code/subagents))

Anthropic's **context-centric decomposition** rule sharpens the same line: split work by *context boundary*, not by *problem/role type*. Delegate only when "context can be truly isolated" (independent research paths, components with clean interfaces, blackbox verification). Do **not** delegate "sequential phases of the same work," "tightly coupled components," or "work requiring shared state" ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).

So the closest thing to a consensus dividing line: **steer inline (skill) when the model must keep reasoning against shared, evolving context and you want to watch/correct it; delegate to a sub-agent when the work is isolatable, produces disposable intermediate noise, needs a hard tool/permission boundary, or can run in parallel — and you only want the summary back.** This matches the question's proposed rule almost verbatim.

## What this means for a three-tier rule (skill → in-process subagent → Herdr sibling session)

The sources support a spectrum ordered by *degree of context isolation and handoff cost*, which maps onto the three tiers — with one important caveat about where the tier boundaries actually fall.

- **Tier 1 — Skill (shared context, inline).** Anthropic + Pocock both put this here: reusable procedure, progressive disclosure, human sees every step, zero handoff cost. Best for work that reasons against the live conversation and needs steering. This is the documented "main conversation" case.
- **Tier 2 — In-process sub-agent (fresh isolated context, returns a summary).** This is exactly Anthropic's subagent: own context window, scoped tools/permissions, verbose work stays out of the main window, parallelisable within one session. The 3–10× token cost and telephone-game risk are the price. Use only when context is *truly* isolatable (context-centric, not role-centric).
- **Tier 3 — Herdr sibling session (separate long-lived session).** Anthropic's docs point beyond subagents to "separate sessions" / background agents / agent teams "for work that needs to keep running in parallel or won't fit in one context window," passing findings between them ([Anthropic, Create custom subagents — "Run parallel research"](https://docs.anthropic.com/en/docs/claude-code/subagents)). This is the natural home for Herdr's sibling sessions: independent, substantial, long-running, human-supervised via a sidebar rather than a returned summary.

Caveats / where a clean three-tier split is contradicted by the sources:

- **The tiers are composable, not mutually exclusive.** A Tier-2 sub-agent can *preload and run Tier-1 skills*. A defined AGENT is frequently "isolated context + fixed tools that executes skills," so "skill vs agent" isn't a fork in the road at the top — it's a question of *where the skill runs* ([Anthropic, Create custom subagents — Preload skills](https://docs.anthropic.com/en/docs/claude-code/subagents)).
- **"Fork" collapses the Tier-1/Tier-2 boundary.** A forked sub-agent has isolated *output* but shared *input context* and reuses the prompt cache — cheaper than a fresh sub-agent. So the jump from Tier 1 to Tier 2 isn't a single step; there's a "keep the context, isolate the noise" half-step in between ([Anthropic, Create custom subagents — Fork](https://docs.anthropic.com/en/docs/claude-code/subagents)).
- **The dividing test is the same at every tier boundary: can the context be truly isolated?** Anthropic's context-centric rule ("split only when context can be truly isolated; never split sequential phases or shared-state work") applies equally to the Tier-1→2 and Tier-2→3 jumps. That single test — not a fixed taxonomy of task types — is what the primary sources actually endorse ([Claude, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)).
- **Not found:** no primary source explicitly names a *three-tier* "skill → in-process subagent → separate session" ladder as a single decision rule. The three tiers are assembled here from separate Anthropic docs (skills doc, subagents doc, multi-agent blog) plus the Herdr/Pocock context; the ladder is a reasonable synthesis, not a quoted framework.
